How it works

Problem

For each participant i and target stop t, the app calculates a journey value T_i(t) for the selected direction.

  • There only: minutes from the participant's start stop to t.
  • Back only: minutes from t to the participant's end stop.
  • Round trip: the sum of both values.

Objective functions

Minimize longest journey

t* = argmin_t max_i T_i(t)

This is the default group metric.

Minimize total journey time

t* = argmin_t sum_i T_i(t)

This favors the lowest combined journey time.

Candidate selection

The first stage uses 1,444 geocoded stops and 2,083,035 precomputed directional stop pairs. These are precomputed typical times, used to select candidates without live routing requests.

Live refinement

The app then queries live DPP journey times for candidate stops at the selected date and time. Ranked results use this live refinement, including the applicable return direction.

Venue search

Nearby places come from Google Places for the selected venue types. Cached results are checked before a live provider query; venue failures do not change the transit ranking.

Heatmap

The reachability layer is Approximate from typical transit times. For everyone, it uses G(t) = max_i T_i(t). Fixed colour bands below the map show the approximate journey time.

Each map location uses its nearest stop and adds an estimated walk to G(t). Walking uses straight-line distance with a 1.2 street-detour factor at 5 km/h. Click a stop point to see its unadjusted stop time.

Changing the participant or visibility does not make live DPP or Google API requests. Stop points remain visible so the source data is clear.

Limitations

The walking estimate does not follow the street network, and the underlying transit matrix is not live. Use the ranked results for live-refined journeys and exact participant times.
